# HRLLC-TSN MAPPO Reimplementation

This folder contains a modular reimplementation scaffold for the paper:

`Toward Deterministic 6G HRLLC: A Multi-Agent DRL-Based Traffic Scheduling Method in HRLLC and TSN Converged Networks`

The workflow is:

1. Windows Python creates or loads the current MAPPO-style model weights.
2. Windows Python calls WSL/Linux.
3. Linux runs the C++ ns-3 simulation with the current weights.
4. The C++ simulator writes a CSV trajectory/results file back to this Windows folder.
5. Windows Python reads the CSV and updates the model weights.
6. The next Linux/ns-3 run uses the updated weights.
7. The loop repeats for the requested number of rounds.

## What Is Implemented

- HRLLC-TSN timing model based on the paper's equations:
  - TSN controller-to-switch latency
  - TSN switch queue ordering using arrival time and wireless channel quality
  - NW-TT to DS-TT latency budget
  - DS-TT gate release time
- HRLLC mini-slot transmission latency
- HARQ retransmission latency
- E2E reliability from Gamma CDF terms
- Paper-aligned retransmission limit `N * d_r < L_k`
- Moving industrial equipment in a circular area.
- Per-equipment large-scale shadow fading redrawn every simulation step.
- Two time-sensitive flow types matching Table III:
  - Type 1: period 5 ms, latency <= 3 ms, 1000 bytes, reliability >= 1 - 1e-7
  - Type 2: period 10 ms, latency <= 5 ms, 1200 bytes, reliability >= 1 - 1e-6
- MAPPO-style model:
  - one actor per equipment
  - two hidden layers
  - two categorical action heads: power requirement factor and retransmission count
  - centralized critic
  - generalized advantage estimation
  - PPO clipped actor update
  - Huber critic loss

## Important Fidelity Notes

This is a close, practical reimplementation of the paper model, not the authors' original source code. The original paper does not publish implementation code in the PDF. The ns-3 C++ portion implements the paper's system equations and scheduling loop. The Python trainer implements the MAPPO-style update in NumPy so it can run on Windows without PyTorch.

The paper leaves several implementation choices unspecified. Those choices, their rationale, and their possible effect on the results are recorded in [ASSUMPTIONS.md](ASSUMPTIONS.md). The active configuration and each campaign manifest record which assumptions were used for that run.

The HRLLC physical layer is equation-level rather than a full 5G-LENA PHY/MAC stack. This keeps the simulation aligned with the closed-form analysis in the paper and makes the repeated Python-C++ training workflow feasible.

## Folder Layout

- `ns3/scratch/hrllc_tsn_mappo.cc` - C++ ns-3 simulator.
- `python/hrllc_tsn_trainer.py` - Windows Python orchestrator and NumPy trainer.
- `scripts/setup_ns3_wsl.ps1` - downloads local CMake if needed, downloads ns-3, builds the simulator.
- `scripts/run_training.ps1` - runs the repeated Windows-Python/Linux-ns-3 workflow.
- `configs/default_config.json` - default paper-like parameters.
- `weights/` - model weights generated by Python.
- `runs/` - CSV results generated by ns-3 and summaries generated by Python.

## Quick Start

### Prerequisites

- Windows 10/11 with PowerShell, Git, Python 3.10+ and WSL 2 with an Ubuntu
  distribution.
- Internet access on the first setup: ns-3 is downloaded by the setup script
  into `external/`, which is intentionally not versioned.

### Fresh clone

```powershell
git clone https://github.com/Taha1778/hrllc-tsn-mappo-ns3.git
cd hrllc-tsn-mappo-ns3
python -m pip install -r requirements.txt
.\scripts\setup_ns3_wsl.ps1
```

`setup_ns3_wsl.ps1` clones ns-3.44, copies this repository's simulator source
into its scratch directory, configures it, and builds `hrllc_tsn_mappo`. It is
safe to rerun after changing the C++ source.

### Smoke test and training

From PowerShell in this folder:

```powershell
.\scripts\start_reproduction_campaign.ps1 -Mode Preflight
.\scripts\run_training.ps1 -Rounds 3 -Iterations 256 -K 8
```

The preflight is the recommended first command on a new device. It verifies
the Python packages and compiled WSL/ns-3 simulator before a long campaign.

The combined run summary will be saved under `runs/` as CSV files.

Generated `runs/` and `weights/` folders are deliberately ignored by Git.
They are reproducible outputs, not required inputs; a fresh run creates them.

## Native Linux and private-cluster execution

The original Windows/WSL workflow remains supported. On a dedicated Linux
worker, first install CPU PyTorch from
`https://download.pytorch.org/whl/cpu`, then run
`python3 -m pip install -r requirements-linux.txt`. Run
`./scripts/setup_ns3_linux.sh` once and then
`./scripts/run_training_linux.sh --preflight`. The Linux runner uses the same
Python trainer and C++ ns-3 source, but calls ns-3 directly rather than through
WSL.

For the approved private college cluster, `cluster/README.md` documents a
containerized Ray workflow. It distributes only independent source-Python
Figure 8 method/K points, assigns each job its own output folder, and labels
the results as `source_python_reference`. It does not reinterpret those outputs
as C++ ns-3 data or permit workers to share `runs/` or `weights/` directories.

If Python reports missing dependencies, install them with:

```powershell
python -m pip install -r requirements.txt
```

Use `-FreshStart` when you want a genuinely new campaign. It deletes only
generated run CSVs and generated model checkpoints, then creates a new random
model at round 0. `-ResetModel` resets the current model and `runs/summary.csv`
without removing the other generated artifacts.
Without `-ResetModel`, training continues from `weights/current_model.npz` and
starts at the next available round number, for example `round_0002.csv`.

The default configuration now uses the paper's MAPPO learning rates: actor
`1e-4`, critic `5e-3`, trajectory length `256`, and `10` updates per
trajectory. During a campaign, the trainer evaluates each checkpoint with
argmax actions on fixed Linux/ns-3 scenarios. `runs/validation_summary.csv` is
used to choose `weights/best_model.npz`, so a lucky training scenario cannot
become the reported best result.

After C++ edits, `run_training.ps1` automatically syncs
`ns3/scratch/hrllc_tsn_mappo.cc` into the ns-3 scratch folder and rebuilds the
simulator before running.

## Quiet, Low-Overhead Campaigns

The runner, trainer, and setup script never beep. Failures are written to
`runs/workflow_status.json` and the campaign error log instead. For the
paper-preserving background workflow, see [WORKFLOW.md](WORKFLOW.md).

## Current Limitation

The simulator uses ns-3 as the Linux C++ discrete-event execution environment,
but the network behavior is the paper's closed-form HRLLC-TSN timing and
reliability model rather than a full packet-level 5G-LENA/TSN queue-disc stack.
This is intentional for this version because the paper's implementation details
are equation-based and the requested workflow needs many repeated training runs.
